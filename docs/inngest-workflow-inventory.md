# Inngest workflow inventory and migration matrix

Generated 2026-10-14 from `src/services/inngest/functions.ts` (50 functions) by `npm run jobs:inventory`. **Every handler was read line by line** in the 2026-10-14 review; guards that live in the service layer were read only at the cited lines and say so. Nothing here was exercised through the native runner except waves 0a/0b (see the smoke tests).

**Timezone note (applies to every row).** Cron expressions are evaluated in **UTC** in both Inngest and the native scheduler (`time.ts` rejects `TZ=`), so `0 13 * * *` is 18:30 IST in both. Business-hour logic inside handlers (`nextBizHourDate`, review campaigns) and `lib/scheduleTime.ts` use the process-local clock (`Date#getHours`), so the worker must run in the **same TZ as the web app** (production is UTC). That latent behaviour is preserved, not changed, by the migration; fixing it is a separate blocker before wave 6.

**Environment parity.** Handlers read env at run time (`LEAD_ENGINE_V2`, `ACCOUNT_PURGE_MODE`, `GBP_LIVE_WRITES_ENABLED`). The worker loads the same `.env.production`; any difference between web and worker env changes behaviour of migrated functions.

## Reading the table

- **Attempts** = Inngest attempts (initial + retries) the adapter reproduces; native backs off exponentially with jitter, capped, then dead-letters (`npm run jobs:admin` lists dead jobs).
- **Sleeps** = count of durable `step.sleep/sleepUntil` call sites found near the handler (the extractor's block boundaries include helper code, so treat as an upper bound). Native sleeps live in the job document.
- **Emits** = events sent via `step.sendEvent`; routed to whichever system owns the target and memoised so a retry does not re-enqueue.
- Wave order, drain rules and cutover conditions: `docs/inngest-migration-plan.md`.

## Residual duplicate windows (exist under Inngest today; not introduced by migration)

1. **External send, then a failure before the step result is persisted** re-runs that step. Atomic-claim-before-send handlers are protected (booking confirmations, review reminders, nurture ScheduledActions, publish, CRM/performance digests). Handlers that send first and record after: `process-whatsapp-message`, `process-followup-job`, `sales-agent-reply`, `support-agent-reply`, `report-agent-reply`, `report-card-deliver`, `process-demo-booking`, the sales drip, the **review-campaign initial send**, `report-ready-notification` and `owner-whatsapp-digest-cron`.
2. **VersionError retry-resend**: the single-step agent repliers send, then `convo.save()`; a concurrent inbound message pushed by the webhook can make `save()` throw, and the retry sends the reply again.
3. **Event-level dedupe is absent** for `reviews/critical-alert`, `reviews/reply-drafted`, `crm/lead-created`, `demo/booked`: a duplicate event produces a duplicate notification.
4. **Usage counters** incremented in a separate step from the action can drift by one.
5. **Inbound webhook retries** from Twilio/Meta are deduplicated at the webhook with `ProcessedWebhookEvent` before any job is enqueued.
6. **Claim-then-dispatch crons** (weekly-content-autopilot, audit-autopilot, performance digest) advance their anchor before dispatching, so a crash loses a cycle instead of duplicating it.

## Functions that need extra care before their wave

- `owner-whatsapp-digest-cron`: double-send if two owners overlap. Needs an atomic claim before wave 4.
- `report-card-deliver`: launches Chromium; verify memory on the target box before migrating.
- `account-hard-purge`: the Razorpay cancel retry ignores the dry-run mode (QA suppression blocks it in staging).
- `booking-agent-reply`: creates real calendar invites. Under QA suppression Calendar create/delete fails closed (the lead is handed to a human), so staging never emails an attendee; without suppression it is live.
